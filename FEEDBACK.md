# Corrections and feedback — keep one factual source

Thanks for checking this working reference. A quick reply is welcome; nobody needs to write a technical report or use GitHub if email is easier.

## The easiest options

**By email:** reply to the message that shared this reference and mention the **document + heading**, what looks wrong/missing, and what the correct information is (if known). Confidential photos, equipment labels, technician notes and operational details should be shared through the approved **private** company channel.

**On GitHub:** if the project owner has enabled Issues, select **New issue → Correction or missing information**. This is useful for ordinary non-sensitive corrections, and the issue can be tracked until the document is updated. **Remember public-repository issues are public.** Never post site-security details, private plant photos, personal data, original HMI screens or internal supplier terms in a public issue.

**Direct file edits:** collaborators who have been given appropriate repository permissions can propose a branch/PR; the repository owner or designated reviewer will check and merge accepted changes. Gemini itself cannot push changes to GitHub.

## What makes feedback actionable

- File and section (or pasted excerpt of the claim).
- Status: **incorrect / incomplete / outdated / possible improvement**.
- Proposed correction in one or two sentences.
- Whether it is **personally observed**, **reported by a colleague**, **on an equipment label**, or **a hypothetical suggestion**.
- Date of observation and responsible reviewer, where relevant.

A correction is not treated as operationally approved until the responsible technical owner validates it. Engineering modifications remain under contractor/site authority.
